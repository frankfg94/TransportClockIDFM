# Itinéraires théoriques du verdict de quartier

La page `/nearby-neighborhood-score` injecte son propre `TravelRoutesProvider` GTFS. Les trajets de transport sont calculés depuis les horaires théoriques. Leurs accès piétons utilisent une source publique commune IGN BD TOPO via la politique `gtfs-access`, indépendante des clés et quotas ORS/Navitia de chaque environnement. Les autres marches du verdict conservent leur politique `ors-only`. L’annexe trafic peut utiliser PRIM après un clic, via le cache partagé `/api/traffic`.

`server/services/walking/ignWalkingMatrix.ts` utilise le profil piéton officiel de la Géoplateforme. Huit destinations sont calculées dans une requête avec 15 points intermédiaires au maximum : les portions aller et retour restent indépendantes et le sens demandé est respecté. Les courts raccordements aux coordonnées exactes sont inclus dans la distance et la durée ; un snap supérieur à 100 m reste explicitement non vérifié. Les paires dirigées partagent un cache borné pour toutes les coordonnées, sans résultat propre à une adresse. Les départs de requêtes sont espacés de 250 ms, conformément à la limite publiée de 5 requêtes/s/IP. Le quota et les échecs restent visibles dans les diagnostics.

Source du contrat : https://cartes.gouv.fr/aide/fr/guides-utilisateur/utiliser-les-services-de-la-geoplateforme/calcul-itineraire/ . Les chargements clients des transports disposent de cinq minutes pour respecter la file publique ; les erreurs et marches estimées restent explicites.

Le scan conserve l’arrivée la plus précoce et l’accès initial au tram le plus court pour chaque première ligne, y compris à bord d’une même course et après correspondance. Deux parcours de mêmes lignes ne sont plus fusionnés avant d’avoir comparé leurs arrêts de montée. À suite de lignes identique, la sélection privilégie l’accès initial le plus court puis le temps calculé. Les minima de changement de véhicule ne sont jamais appliqués à l’accès initial ; seuls les cheminements GTFS explicites peuvent prolonger cette marche.

Un accès à une ligne par cette même ligne ne constitue pas une alternative de proximité, même si un autre transport la précède. Le filtre examine tous les véhicules du trajet avant de sélectionner les alternatives : un autre tram ou un bus qui rejoint la ligne sans l’emprunter reste admissible. Le verdict retient ensuite le point d’accès le plus rapide par ligne, quel que soit son mode. Les trajets vers une destination précise (pôle GPE ou Châtelet) conservent leur parcours complet. Si une ligne possède un arrêt immédiatement proche de l’adresse selon les coordonnées chargées, seul ce signal physique est conservé pour cette ligne ; son temps de marche routé peut ensuite remplacer l’estimation sans faire disparaître la proximité. Les détails identifient le premier arrêt de montée et distinguent les marches estimées.

Pour les arrêts de tram ou de câble à deux minutes cartographiques au maximum, l’accès initial utilise explicitement la marche estimée à 80 m/min, arrondie à la minute supérieure. Cette règle commune s’applique avant de vérifier qu’une course est attrapable et aussi au signal d’accès à pied ; elle n’est pas limitée à une ligne ou une gare. Les détails affichent `≈` et une preuve dérivée. Les autres accès utilisent le réseau piéton ; les bus continuent d’exiger une marche documentée.

Les futurs pôles situés dans le rayon de recherche restent documentés lorsque leur trajet dépasse les trente minutes de proximité : ils deviennent des repères neutres, sans bonus de proximité et sans masquer les accès actuels. Les loaders des sous-tâches sont intégrés directement à la catégorie Transports.

## Artefacts et publication

`npm run gtfs:update` construit les géométries, les horaires et le nouvel index de routage à partir du même ZIP officiel. L’index utilise les courses complètes du timetable, les calendriers et exceptions, les identifiants officiels des arrêts, `transfers.txt` et `pathways.txt` lorsqu’ils existent.

Le descripteur `current.json.routing` expose le schéma, le chemin immuable, les dates de couverture, le nombre de connexions, de fichiers et d’octets. Son chemin est `routing/v1/<sha256>/<generation>`. `index.json` contient les arrêts, services, lignes, correspondances et la liste des tranches horaires. Les fichiers `<heure>-<partie>.json` contiennent au plus 65 536 segments, triés par départ, en entiers 32 bits compressés avec gzip. Les références des courses sont conservées.

La publication envoie tous les artefacts avant de remplacer `current.json`, aussi bien en local que sur R2. Un échec de publication du routage conserve les anciens manifestes. `npm run gtfs:stage-pages-assets`, inclus dans `npm run build`, copie uniquement les générations actives dans les assets Cloudflare Pages. Le lecteur serveur réutilise le lecteur GTFS partagé : stockage local, R2 ou binding `ASSETS` de Cloudflare.

## Moteur partagé et calcul dans le navigateur

Le moteur pur se trouve dans `shared/gtfs/`. Le serveur lui injecte son stockage GTFS et ses matrices ORS. Dans un navigateur compatible, le verdict utilise le même moteur dans `neighborhoodGtfs.worker.ts`, pour éviter les limites CPU/mémoire des fonctions Cloudflare Pages. Aucun horaire ni temps de trajet n'est remplacé par une estimation de transport.

Le Web Worker lit les artefacts publics `/_gtfs-data/`, conserve les fichiers immuables dans Cache Storage et recharge le manifeste courant chaque minute. Trois lots de transports de journée, un lot de nuit et un lot d'autres catégories peuvent attendre leurs marches en parallèle, avec au plus deux arbres en mémoire. Les fréquences et derniers passages ont un Worker et une file séparés. Les accès et sorties utilisent `/api/walking/matrix` avec `gtfs-access` et le sens de marche explicite. Si aucune source piétonne ne répond, seule la marche est estimée et son statut reste indiqué. Les messages du Worker utilisent le contrat JSON pour accepter les coordonnées réactives Vue.

Le premier calcul peut télécharger plusieurs tranches du dataset. Les suivantes réutilisent le cache local du navigateur. Une date hors couverture, un artefact absent ou l'absence réelle d'itinéraire dans la fenêtre conserve un état explicite ; les données théoriques ne peuvent pas justifier un temps inventé. Les environnements sans Web Worker gardent l'API serveur.

## API serveur

`POST /api/neighborhood-journeys` accepte une origine, une date civile `YYYYMMDDTHHMMSS` dans `Europe/Paris`, de 1 à 64 destinations et les modes autorisés. Une destination peut fournir `destinationRef` pour identifier officiellement une station. Avec `arrivalAtPlatform=true` et une référence reconnue, le trajet s'arrête au dernier débarquement dans cette station ; aucune marche de sortie vers son centre géographique n'est ajoutée. Les identifiants monomodaux restent distincts des identifiants de quais. Les caches du fournisseur distinguent cette politique d'arrivée.

Pour un accès à une ligne actuelle, `destinationLineId` impose un arrêt réellement desservi par cette ligne dans les services GTFS scannés. L'arrivée sur une autre ligne de la même gare ne suffit pas : le cheminement final publié est conservé jusqu'à l'arrêt cible, sans monter dans la ligne recherchée. Les arrivées sur les autres quais du pôle restent disponibles pour reconstruire ce dernier cheminement, même si un trajet empruntant déjà la ligne cible arrive plus tôt. Une interdiction de correspondance n'est pas contournée. Ce paramètre distingue également les abonnés et entrées de cache d'un même pôle. Les grandes gares et futurs pôles sans service actuel gardent leur politique d'arrivée par destination.

Le moteur emploie un [Connection Scan Algorithm](https://arxiv.org/abs/1703.05997) d’arrivée au plus tôt. Il lit les tranches utiles et fusionne les jours de service nécessaires, au lieu de parcourir chaque ligne pour chaque destination. Les heures GTFS supérieures à 24 h et les changements d’heure utilisent l’ancre GTFS « midi local moins douze heures ». Les restrictions de montée/descente et les correspondances génériques ou spécifiques à une ligne/course sont vérifiées avant l’embarquement.

Un arbre origine/date/modes répond à toutes les destinations. Les requêtes simultanées partagent sa promesse. Le cache conserve au plus deux arbres pendant dix minutes ; son identité inclut le chemin des artefacts, la génération du manifeste et l’époque du cache GTFS. Le fournisseur de la page groupe les demandes et conserve les réponses pendant une minute, avec invalidation à réception d’une nouvelle version. L’annulation d’une adresse empêche l’application de ses anciennes réponses.

La lecture conserve au plus trois tranches horaires préchargées et le scan reçoit les connexions par lots de 1 024. Les jours de service restent fusionnés dans l’ordre des départs. Le graphe compact de correspondances sert aussi à consulter les durées minimales ; aucune seconde table de chaînes pour toutes les paires d’arrêts n’est conservée. Ces bornes réduisent les allocations et les lectures séquentielles du Worker sans changer les itinéraires recherchés.

Les files d’attente par destination sont contournées seulement pour ce fournisseur. L’option `batchQueries` du résolveur de pôles lui permet de présenter toutes ses destinations au fournisseur, qui envoie des lots de 64. Les abonnés d’un même point sont dédupliqués, y compris avec annulation et lorsque l’origine porte des métadonnées différentes. Le fournisseur piéton de cette page groupe aussi les pôles par origine et par portée d’annulation avant d’appeler les matrices ORS.

Les accès et sorties utilisent les matrices ORS dirigées et les caches piétons partagés. La politique optionnelle `ors-only` est aussi transmise aux lieux, centres commerciaux, parcs et futurs pôles du verdict. Une indisponibilité ORS produit une marche explicitement estimée, sans repli PRIM et sans enregistrer cette estimation comme parcours documenté.

Un quota ORS épuisé est identifié séparément d'une erreur réseau. Les nouvelles tentatives sont suspendues pendant le délai de reprise, tandis que les parcours déjà en cache restent utilisables. Un nouvel identifiant de lieu peut réutiliser la même matrice géographique. La relance des sources peut remplacer les estimations par des parcours documentés.

## Couverture et présentation

### Frontière impérative : accès final et correspondances intermédiaires

**Instruction pour les mainteneurs et agents IA : le calcul physique de marche finale est réservé aux destinations portant `destinationLineId`. Ne pas le substituer aux règles de correspondance ou d’embarquement de `connectionScan`.** Les trajets complets et les destinations GPE continuent à utiliser les contraintes GTFS du scan partagé. Leur attente intermédiaire ne doit pas être supprimée par cette correction d’accès.

Le nouvel index conserve séparément les entrées, les nœuds intermédiaires et les chemins dirigés de `pathways.txt` (`pedestrianGraphVersion: 1`). Ils sont ajoutés après les arrêts horaires et ne deviennent pas des arrêts d’embarquement. Les minima de `transfers.txt` restent des contraintes séparées. Les anciens artefacts restent lisibles ; régénérer localement avec `npm.cmd run gtfs:update -- --local --force --reindex` pour activer le graphe physique, sans mélanger des archives de dates différentes.

Après le scan partagé, l’accès à une ligne compare les chemins complets : sortie officielle éventuelle du point d’arrivée, marche extérieure sur voirie, entrée adaptée et cheminements officiels jusqu’au point GTFS de la ligne. `stop_access` et les sens sont conservés. Un point monomodal agrégé ne certifie pas un quai directionnel individualisé. Toutes les entrées compatibles sont examinées ; les relations GTFS entre stations différentes sont incluses. Le vol d’oiseau ordonne les demandes sans éliminer d’entrée, et sert seulement de repli estimé. Les tronçons sont calculés en secondes, sans minute minimale ajoutée devant une entrée.

Les demandes piétonnes sont groupées par origine, découpées à 64 destinations, dédupliquées et mises en cache par paire dirigée ; les recherches intérieures sont réutilisées par version d’index. Les recherches des arrivées et sorties indépendantes attendent le fournisseur en parallèle : les sérialiser peut faire dépasser le délai du verdict dans une grande gare. Le fournisseur conserve ses lots et sa limitation de débit. Aucun appel piéton n’intervient dans le scan lui-même. Un seul résultat consolidé est publié après les cheminements, avec le loader Transports existant. Un parcours extérieur estimé ou un cheminement intérieur incomplet reste un repère sans bonus et ne remplace pas un accès documenté pour la note. Le minimum GTFS peut rester visible comme repère incomplet, jamais comme une marche certifiée. Aucun délai lié au prochain train n’est ajouté à une simple arrivée au point de transport.

Le verdict recherche les transports structurants dans un rayon de 7 km, y compris les trams accessibles par correspondance. Il évalue toutes les destinations admissibles, indépendamment des limites de badges de la carte, puis affiche le meilleur accès par ligne et tronçon physique. Les topologies complètes de l’API sont mises en cache indépendamment des fréquences projetées sur une station. Le découpage partagé des fréquences distingue branches et tronc commun ; les missions, fréquences et terminus intermédiaires ne créent pas de branche. Le rattachement utilise le quai réellement atteint après la dernière marche et les correspondances d’identifiants existantes. Une bifurcation appartient au seul tronçon commun adjacent, sinon à un groupe de jonction distinct. Une topologie absente conserve le regroupement par ligne ; un arrêt ambigu reste non classé, sans bonus de branche supplémentaire. Un arrêt au pied de l’adresse masque seulement les autres accès à son propre tronçon.

Chaque tronçon admissible contribue une fois à la composante de diversité existante : coefficient 1, ou 0,5 pour un accès bus de plus de 15 et jusqu’à 30 minutes. Ces coefficients ne sont pas des points ajoutés directement à la note sur 10. Les nombres de lignes et de modes, les fréquences, la régularité et la condition de note exceptionnelle restent dédupliqués par ligne. Au-delà de 30 minutes, l’accès est conservé comme repère neutre sans influencer aucune composante de la note. L’option `includeContextAccess` du résolveur est activée uniquement par le verdict et désactivée par défaut ; les alternatives de bus conservent également leurs parcours longs. Le scan retient ces accès dans son horizon existant de quatre heures, indépendamment de l’admissibilité au bonus.

Les signaux internes restent identifiés par ligne et gare finale pour les faits GPE : un futur pôle regroupe seulement les informations actuelles à la même gare, sans masquer une autre branche. Le meilleur accès par tronçon est sélectionné avant cette suppression pour ne pas promouvoir artificiellement une autre gare du même tronçon. Les parcours vers une destination GPE conservent leurs correspondances complètes ; un parcours empruntant déjà une ligne actuelle ne devient pas un nouvel accès à cette ligne. Les alternatives de tram sont conservées à travers les correspondances ferroviaires vers les destinations précises, même lorsqu’un bus arrive plus tôt.

Chaque famille de calcul de transport possède un indicateur de chargement avec spinner (pôles, grandes gares, bassins d’emplois, nuit, branches, fréquences, derniers passages, projets et régularité), directement dans la section Transports. Le chargement des trajets et horaires peut durer jusqu’à cinq minutes ; les bornes métier de durée de trajet restent distinctes de ce délai réseau. La publication par lots et le cache des arbres GTFS restent inchangés. Les parcours piétons documentés et leur version de source sont conservés dans le navigateur pendant cinq minutes, y compris entre rechargements ; les estimations ne sont pas persistées et le diagnostic à froid contourne ce cache.

Le verdict conserve ses repères : prochain jour ouvré à 09:00 et prochain 03:00 pour Noctilien, en heure de Paris. La note retire seulement l’attente initiale. Les détails affichent la durée totale, la marche, toutes les attentes, les correspondances, la date de référence et la version GTFS.

Les Noctiliens ont un calcul indépendant dans `shared/gtfs/nightAccess.ts`, chargé par `noctilienAccess.ts`, avec son propre Worker et son loader « Calcul des accès à pied aux Noctiliens ». L’accès ne doit pas être déduit d’un trajet vers un arrêt proche : ce trajet peut être une simple marche, ou atteindre cet arrêt après une autre ligne. Le calcul lit les horaires actifs de chaque ligne de nuit proche (rayon existant de 2,5 km, sans limite de seize destinations), y compris les courses commencées la veille après 24:00. Il mesure la marche IGN vers les points d’embarquement GTFS, vérifie un départ attrapable après cette marche dans l’horizon existant, et conserve le meilleur accès documenté par ligne et sens. Une marche de quinze minutes ou plus n’est pas admissible ; une estimation seule ne crée pas le fait positif. Les détails conservent un vrai segment de course et son attente, qui ne font pas partie du temps de marche affiché. Les calendriers et caches de fichiers GTFS ainsi que les caches piétons dirigés sont réutilisés ; aucun scan complet du réseau n’est exécuté pour cet accès. Une ancienne adresse ne peut pas appliquer ses résultats et l’échec d’une source n’est pas assimilé à une absence de ligne.

Les seuils d'accès aux pôles du verdict GTFS utilisent aussi cette durée après retrait de l'attente initiale. Un futur pôle peut reprendre la référence d'une station actuelle lorsqu'un unique nom officiel ou alias normalisé correspond dans le rayon de rattachement existant. Cela permet de mesurer l'accès au quai actuel sans inventer les horaires de la future ligne.

Le même rattachement s'applique aux stations de la carte qui ne possèdent qu'une référence de quai NeTEx non reconnue par le GTFS. Une référence officielle déjà présente est prioritaire ; un nom partiel, une station éloignée ou plusieurs références possibles ne permettent pas de rattachement. Cette règle reste propre aux requêtes groupées du verdict.

Les noms et alias officiels sont indexés une seule fois par résolution groupée, uniquement si une destination a besoin du rattachement. Les pôles actuels et futurs partagent cet index ; les sondes suivantes ne parcourent que les homonymes. L'index appartient au lot courant pour conserver la bonne version du catalogue.

La sélection des grandes gares utilise la même normalisation des accents, espaces et signes de ponctuation sur leurs noms et alias. Un tiret typographique dans un nom officiel ne doit pas empêcher de lancer sa sonde de trajet.

Deux segments consécutifs sur la même ligne restent distincts lorsque leurs courses officielles diffèrent. Les détails indiquent le changement de train, la gare, l'attente et les missions disponibles. Un trajet direct peut ainsi arriver plus tard qu'une combinaison express puis omnibus, selon le départ de référence ; aucune durée de trajet ou de correspondance n'est remplacée par une valeur propre à une gare.

Une durée issue de `transfers.txt` est présentée comme un minimum de correspondance GTFS, distinct de la marche mesurée : ce minimum peut inclure une marge, conformément à la [spécification GTFS](https://gtfs.org/documentation/schedule/reference/#transferstxt). Les nouveaux artefacts conservent les cheminements physiques dans `pathways`, séparément des contraintes de correspondance ; les anciens artefacts peuvent encore utiliser `pathwayTransferIndices`. Un cheminement plus court ne permet pas d'embarquer avant le minimum de correspondance officiel dans un trajet complet. Aucun temps spécifique à une station n'est codé en dur.

Le calcul est borné à quatre heures, avec un rayon d’accès de 1 200 m et au plus vingt minutes par accès, sortie ou marche de correspondance. Il conserve une alternative ayant pris un transport, ainsi que les arrivées Noctilien par ligne, même lorsqu’une marche directe est plus rapide. Il ne constitue pas une recherche exhaustive de tous les itinéraires possibles.

Les statuts distinguent résultat disponible, partiel, artefacts manquants, date hors couverture et absence de trajet dans la fenêtre. Aucune de ces situations ne déclenche un fournisseur temps réel. Les services nécessitant une réservation et les changements en restant dans le véhicule (`transfer_type` 4/5) sont exclus et signalés par une couverture partielle. Les connexions de marche entre quais du même parent sans durée officielle sont estimées. Cette réserve est volontairement conservatrice à l’échelle du dataset.

## Synthèse documentaire

La première requête documentaire utilise `includeWalking=0`. Sécurité et environnement deviennent utilisables dès cette réponse, indépendamment des trajets. L’enrichissement piéton arrive ensuite et ne recalcule que les catégories concernées. Les échecs peuvent être relancés par source, et les requêtes de l’ancienne adresse sont annulées.

Les sondes de fréquence et de dernier passage attendent que cette première réponse documentaire soit terminée. Leur file ne conserve qu'une requête horaire active à la fois : la lecture d'une grande ligne ne doit pas faire échouer simultanément plusieurs sources dans le même Worker serveur. Les trajets du navigateur continuent indépendamment de cette file.

La commune est obtenue depuis les géométries IRIS lorsque les correspondances donnent un unique code communal. L’API Géo reste disponible seulement lorsque cette correspondance manque ou est ambiguë. La fraîcheur documentaire dépend du statut des sources officielles, et non de l’âge de 24 h du fichier compilé. Chargement, erreur, absence de couverture et obsolescence sont des états distincts.

Une catégorie documentaire vide après une réponse réussie n'est pas une source en échec. Sa ligne facultative est omise du diagnostic si d'autres sources alimentent cette catégorie. Les sources obligatoires, les chargements, les erreurs et l'obsolescence restent visibles.

## Vérification

Les tests dédiés couvrent les courses directes, correspondances et branches, permissions spécifiques, modes, restrictions, calendriers et exceptions, minuit, changement d’heure, artefacts incomplets, ORS indisponible, échec documentaire et changement d’adresse. Ils interdisent les tentatives réseau PRIM et vérifient séparément la politique partagée par défaut et l’annexe sur clic. `tests/gtfsUpdate.test.ts` vérifie notamment l’ordre de publication et les manifestes conservés après un échec de routage.

Commandes utiles sous Windows :

```powershell
npm.cmd run gtfs:update -- --local
npm.cmd run check:data
npm.cmd run tsc
npm.cmd run build
npm.cmd run test -- tests/neighborhoodGtfsRouting.test.ts tests/neighborhoodGtfsProvider.test.ts tests/neighborhoodWalkingPolicy.test.ts tests/neighborhoodTrafficAnnex.dom.test.ts tests/neighborhoodDocumentaryProgress.dom.test.ts
node --max-old-space-size=64 --expose-gc --import tsx scripts/gtfs/benchmark-neighborhood-routing.ts
```

Le benchmark local utilise une adresse publique à Châtillon et des accès estimés, sans aucun réseau. Sa date de référence doit être située dans la couverture du manifeste actif ; les mesures de heap Node ne sont pas des mesures de mémoire du Worker Cloudflare.
